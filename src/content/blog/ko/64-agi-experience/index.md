GPT‑6 Astra를 계기로 AGI에 관심을 갖는 개발자가 늘어날 수 있다고 생각한다. 특히 사용자가 구현 방법을 정해주지 않았는데도 모델이 설계 방향을 찾고, 실행 가능한 결과까지 가져오는 경험에 주목한다. 사람이 직접 내려야 했던 판단을 얼마나 맡길 수 있는지가 달라지기 때문이다.

[GPT‑6 출시 분석](/blog/62-gpt-6-astra/)에서는 기능과 비용을 살펴봤다. 이 글에서는 AGI를 이해하는 기준부터 정리하고, 어떤 작업 경험이 그 가능성을 떠올리게 하는지 살펴본다. 이어서 기존 모델을 쓰던 사람이 무엇을 다르게 맡기고, 기존 구성의 어느 부분을 고쳐볼 수 있는지 설명한다.

자료 확인일은 **2026년 9월 6일**이다. 공개 연구와 OpenAI의 문서·시연을 바탕으로 한 분석이며, 모델 간 직접 비교 실험은 아니다. 아래 하네스 재설계는 원리를 설명하기 위해 만든 가상 예시다. GPT‑6 이후 AGI 관심이 실제로 증가했다는 통계나 AGI 달성 판정을 제시하는 글도 아니다.

## AGI를 판단할 때 나눠볼 것

AGI는 Artificial General Intelligence, 범용 인공지능을 뜻한다. 이 글에서는 여러 종류의 낯선 지적 과제에 지식과 방법을 적용하는 능력에 초점을 둔다. 특정 문제의 정답률만으로 판단하기에는 다뤄야 할 범위가 넓다.

Google DeepMind의 *Levels of AGI* 연구는 능력의 깊이와 범위를 구분하고, 이를 실제로 얼마나 자율적으로 사용하도록 할지도 별도로 다룬다. 여기서는 이 틀을 빌려 세 질문으로 풀어본다. 하나의 연구 틀이며, 아래 표는 그 논문의 등급표를 옮긴 것이 아니다. [연구 소개](https://deepmind.google/research/publications/66938/)

| 기준 | 작업에서 확인할 질문 |
|---|---|
| 범용성 | 익숙한 예제에서 벗어나도 필요한 지식과 방법을 찾아 적용하는가? |
| 숙련도 | 결과가 해당 분야의 실무 검토를 통과하는가? |
| 자율성 | 사람이 다음 단계를 계속 알려주지 않아도 진행하고, 문제가 생기면 복구하는가? |

코드를 잘 쓰는 것, 다양한 분야를 다루는 것, 개입 없이 일을 끝내는 것은 각각 확인할 항목이다. 실행 권한을 많이 줬다는 사실도 능력의 증거가 되지는 않는다. 반대로 승인을 기다리는 동작 하나만 보고 능력이 부족하다고 판단하기도 어렵다. 사용자가 정한 운영 조건을 따르는 것일 수 있다.

## ARC-AGI-3의 높은 점수는 무엇을 말해주나

OpenAI 발표의 ARC-AGI-3 결과는 Astra 99.9%, Sol 7.8%다. 낯선 과제에 적응하는 능력을 살펴보는 평가에서 큰 차이가 나온 만큼 AGI 논의에서 주목할 근거가 된다. 다만 발표는 하네스의 두 가지 일반 설정을 바꿨다고 설명하고, 평가별 최고 추론 결과를 제시한다. 모델 이름만 교체한 모든 실제 작업에서 같은 차이가 난다는 뜻은 아니다. [공식 발표와 평가 조건](https://openai.com/index/gpt-6-astra/)

이 점수만으로 여러 분야의 실무를 자율적으로 해낼 수 있다고 판단하기는 어렵다. 종류가 다른 과제에서도 잘하는지, 실패하면 스스로 복구하는지를 더 봐야 한다. 실제 사용에서는 설계 방법을 고르고 여러 도구로 작업을 이어가는 과정에서 이런 능력을 확인해볼 수 있다.

## 해법을 설명하지 않았는데 설계 방향을 찾는다

설계 판단을 맡기는 경험은 다음과 같은 요청에서 드러날 수 있다.

```text
에이전트에 규칙을 추가할수록 프롬프트가 길어지고 확인 턴이 늘어난다.
기존 작업 실행기는 유지하면서, 금지한 행동을 확실히 차단하고 싶다.
현재 코드와 실행 기록을 읽고 구조를 개선해줘.
```

이 요청에는 어느 언어로 무엇을 구현할지 정해져 있지 않다. 모델은 규칙을 짧게 다시 쓰거나 중복 검사를 줄일 수도 있다. 더 큰 변경으로는 기계적으로 판정할 수 있는 규칙을 호스트 프로그램에 옮기고, 모델에게는 작업의 의미를 판단하는 부분을 남길 수 있다.

후자의 제안이 실제 코드와 제약에 맞는다면, 사용자는 자신이 설명하지 않은 해결 경로를 받은 것이다. 여기서 평가할 능력은 **요구를 해석하고, 기존 구조를 조사하며, 서로 다른 구현 방법 중 적합한 것을 고르는 판단**이다. 빠뜨린 내용을 무조건 추측하는 것은 좋은 설계가 아니다. 결과를 크게 바꿀 모호함은 질문하거나 근거를 찾아 해소해야 한다.

이 설계 원리는 GPT‑6에서 처음 생긴 것이 아니다. 다른 모델도 제안할 수 있다. 달라졌는지 확인할 것은 같은 자료를 주었을 때 얼마나 적은 보충 설명으로 적절한 제안을 하고, 구현과 검증까지 일관되게 이어가는가다.

### 하네스가 커져도 모델의 부담은 줄 수 있다

하네스는 모델이 일하도록 도구, 상태 관리, 실행 절차와 통제를 연결하는 주변 프로그램이다. 가상 예시에서 작업 진행은 기존 Agent Loop가 맡고, 별도의 호스트 프로그램이 실행 요청을 검사한다고 하자.

| 역할 | 프롬프트에 집중한 구성 | 호스트 검사를 추가한 구성 |
|---|---|---|
| 할 일과 방법 결정 | 모델과 기존 Agent Loop | 모델과 기존 Agent Loop |
| 쓰기 대상 제한 | 모델에게 허용 경로를 설명 | 실제 쓰기 권한과 도구 실행 경로에서 검사 |
| 승인 상태 확인 | 대화 내용을 모델이 해석 | 해당 작업·대상에 연결된 승인 기록을 실행 직전에 확인 |
| 실패 처리 | 긴 로그를 읽고 다음 행동 결정 | 호스트가 상태를 기록하고 모델에 필요한 오류와 조회 수단 제공 |

정책 저장, 실행 검사, 감사 기록을 추가하면 전체 프로그램은 커질 수 있다. 하지만 모델이 매번 읽고 판단하던 일을 코드가 처리하면 반복 입력과 확인 대화를 줄일 여지가 생긴다. **프로그램의 크기와 모델이 처리하는 문맥의 크기는 별개로 설계할 수 있다.**

모든 규칙을 옮길 수는 없다. 경로·권한·승인 유효성처럼 명확하게 판정할 항목은 코드로 다루기 좋지만, 변경이 사용자의 의도에 맞는지 같은 판단에는 맥락이 필요하다. 모델에도 허용된 작업과 거절 이유를 이해할 최소한의 설명은 남겨야 한다.

네이티브 바이너리나 Bash로 만들었다는 사실만으로 통제가 강해지지도 않는다. 별도 셸이나 다른 도구가 검사를 우회할 수 있다면 금지 행동은 여전히 가능하다. 정책과 승인 기록을 에이전트가 임의로 바꾸지 못하게 하고, 검사 실패 시 실행이 중단되는지도 확인해야 한다. 이 예시의 목표가 금지 행동 통제이므로 필요한 설계 조건이다.

효과를 확인하려면 허용 작업이 계속 성공하는지, 금지 작업이 차단되는지부터 본다. 그다음 토큰과 사람의 개입을 비교한다. 호스트가 매번 거대한 로그를 반환하거나 과도하게 거절하면 절감 효과가 사라질 수 있다. 기능 수나 턴 수만 세지 말고, 같은 일을 제대로 끝냈는지까지 비교해야 한다.

## 여러 도구로 하나의 결과를 완성한다

확인할 수 있는 공개 사례도 있다. Thomas Ricouard는 OpenAI 개발자 블로그에서 간단한 주택 요청을 Astra와 Codex로 편집 가능한 Blender 장면으로 만들었다고 설명한다. 모델은 렌더를 확인하며 일부 오류를 수정했고, 이후 사용자의 요청에 따라 평면도와 공간을 발전시켰다. [건축 시각화 사례](https://developers.openai.com/blog/architectural-visualization-with-astra)

여기서 주목하는 경험은 원하는 분위기를 소프트웨어 조작과 시각적 검토로 연결하는 것이다. 코드를 만들고, 실행 결과를 보고, 목표에 맞게 수정하는 과정이 이어지면 사용자가 단계 사이를 연결하는 부담이 줄 수 있다.

다만 이 자료는 공급자가 공개한 사례다. 사람의 후속 지시가 있었고, 전체 집을 한 번에 완성했다는 기록도 아니다. 보기 좋은 장면이 실제 건축 설계의 검증을 통과했다는 뜻은 더더욱 아니다. 이 사례는 여러 도구를 연결하는 경험을 보여주지만, 독립적인 모델 비교나 전문 자격 수준의 증거로 사용할 수는 없다.

하네스 예시와 이 사례를 함께 보면 AGI를 떠올리는 이유를 설명할 수 있다. 사람은 자신이 익숙하지 않은 구현 방법까지 포함해 결과를 요청한다. 모델이 그 간격을 메우면, 다음에는 더 큰 단위의 일을 맡겨보게 된다. 이런 경험의 축적이 AGI에 대한 관심을 키울 수 있다는 것이 내 해석이다.

## GPT‑6에서 기존 사용자에게 달라질 수 있는 부분

OpenAI는 Astra가 GPT‑5.6 Sol보다 긴 작업의 일관성과 지시 이행에서 개선됐다고 설명한다. 동시에 확인 질문이나 검증이 과해질 수 있고, 스킬과 `AGENTS.md`의 영향을 더 민감하게 받을 수 있다고 안내한다. 이는 공급자의 설명이다. [공식 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model)

자신의 기존 구성이 어느 부분에서 막혔는지에 따라 실험할 변화도 달라진다.

| 기존 작업에서 겪던 문제 | 시도할 활용 | 수정할 구성과 확인할 결과 |
|---|---|---|
| 사람이 구현 방법을 매번 지정 | 목표와 제약을 주고 설계 대안·선택 이유까지 요청 | 고정 절차를 강제하던 지시를 점검하고, 제안의 적합성과 보충 설명 횟수 비교 |
| 파일 조사·수정·검증 사이에 작업이 끊김 | 같은 완료 기준 아래 조사부터 검증까지 맡김 | 자료·도구 접근과 완료 조건을 연결하고, 누락된 단계와 사람의 개입 기록 |
| 테스트나 조회를 기다리는 동안 정지 | 결과와 무관한 작업을 대기 중 진행 | 비동기 도구와 결과 연결을 지원하고, 실제 경과 시간 비교 |
| 진행 중 요구 변경을 다음 턴까지 보류 | 작업 중 수정 지시를 전달 | 이를 지원하는 앱 또는 API 연결을 사용하고, 최종 결과의 범위 반영 확인 |

표의 앞 두 행은 평가해볼 활용 제안이다. 뒤 두 행은 실행 기능도 필요하다. API의 비동기 도구 호출은 `async: true`로 지정하고, 호스트가 작업을 실행한 뒤 원래 `call_id`에 결과를 연결한다. 모델 이름만 바꿔서는 기존 실행 루프가 이 역할을 자동으로 맡지 않는다. [비동기 호출 문서](https://developers.openai.com/api/docs/guides/async-tool-calling)

작업 중 지시를 보내는 Mid-turn steering은 Astra의 Responses API WebSocket 연결에서 지원된다. 이미 시작한 도구를 취소하거나 완료한 외부 작업을 되돌리는 기능은 아니다. 앱을 사용하는 독자는 해당 앱의 지원 여부를, 직접 연동하는 개발자는 지시 접수와 후속 실행 처리를 확인해야 한다. [Steering 문서](https://developers.openai.com/api/docs/guides/steering)

Claude나 Gemini 사용자는 이 표를 자신의 작업을 비교할 질문으로 사용할 수 있다. 여기에는 같은 조건에서 측정한 타사 모델 결과가 없으므로 Astra의 일괄적인 우위를 주장하지 않는다. 같은 회사의 이전 모델을 쓰던 경우에도 자신의 작업에서 개선되는지 확인하는 절차는 필요하다.

## 기존 구성은 이 순서로 고쳐본다

먼저 실제로 반복하는 과제 하나와 완료 기준을 고른다. 기존 모델·버전·추론 설정·도구·권한을 기록하고 기존 구성을 기준선으로 실행한다. Astra로 바꿀 때는 접근 가능 여부와 API·도구 스키마의 호환성을 확인한다. `none` 추론 설정은 Astra에서 지원하지 않으므로 해당 설정을 사용했다면 수정이 필요하다. [모델 문서](https://developers.openai.com/api/docs/models/gpt-6-astra)

그다음 기존 지시문에서 목적과 절차를 구분한다. 아래는 설계 판단을 맡겨보기 위해 만든 지시문 예시다.

```text
목표: 기존 실행기를 유지하며 반복 문맥과 불필요한 확인을 줄인다.
자료: 현재 코드, 규칙 파일, 성공·실패 실행 기록을 읽는다.
설계: 대안을 비교하고 각 책임을 모델과 호스트 중 어디에 둘지 설명한다.
변경: 격리된 로컬 사본에서 구현한다. 정책이나 권한을 완화하지 않는다.
검증: 허용·금지 동작을 유지하고, 같은 과제의 사용량과 개입 횟수를 비교한다.
질문: 설계 결과를 크게 바꿀 정보가 없으면 질문한다.
완료: 변경 내역, 검증 결과, 남은 한계를 함께 제시한다.
```

과거의 실패를 막으려고 붙인 “매 단계에서 확인”, “항상 전체 테스트” 같은 문구가 있다면 적용 범위를 구체화한다. 예를 들어 되돌릴 수 있는 로컬 작업과 외부 게시를 구분하고, 검증 범위를 변경의 영향에 맞춘다. 팀에서 요구하는 필수 검증과 실제 권한 제한은 유지한다. 설명이 짧아도 이해하는 능력을 평가하더라도 목표·자료·금지 사항까지 생략할 이유는 없다.

실행 구조의 변경은 그 뒤다. 반복 규칙 중 코드로 판정할 수 있는 항목부터 작은 단위로 옮기고, 모델에게 보내는 결과를 정리한다. 토큰 절감이 목적이라면 바이너리로 다시 만드는 것부터 시작할 필요는 없다. 기존 호스트에서 같은 책임 분리가 가능한지 먼저 본다. 잘 동작하는 Agent Loop도 유지하면서 개선 원인을 좁혀볼 수 있다.

비교는 기존 구성, 모델만 교체한 구성, 프롬프트·호스트까지 조정한 구성으로 나눈다. 같은 입력과 완료 기준으로 반복 실행하고, 실패한 시도까지 포함한 토큰·총비용·시간·사람의 수정량을 기록한다. 설정 차이도 남긴다. 품질과 금지 행동 통제를 유지하면서 개선되는 변경만 채택한다. 이 순서는 제안한 실험 절차이며, 이 글에서 직접 측정한 결과는 아니다. 자세한 평가 구성은 [AI Eval 가이드](/guides/ai-eval/)로 연결한다.

## AGI의 가능성을 보려면 성공 이후를 확인해야 한다

인상적인 결과 다음에는 비슷하지만 조건이 다른 과제를 맡겨봐야 한다. 의존성이 바뀌거나 정보가 부족할 때도 방법을 찾는지, 도구가 실패하면 복구하는지, 틀린 가정을 지적받으면 설계를 수정하는지 살펴본다. 첫 결과의 놀라움이 반복 가능한 능력인지 확인하는 과정이다.

METR의 시간 지평 평가는 일정 성공 확률로 해결할 과제의 난도를 인간 전문가의 소요 시간으로 표현한다. AI가 그 시간 동안 자율적으로 일했다는 뜻은 아니다. 대상도 주로 소프트웨어·머신러닝·사이버보안 과제이므로 모든 직무로 확대할 수 없다. 여기서는 평가 관점만 참고하며 GPT‑6의 측정값을 인용하지 않는다. [평가 방법과 한계](https://metr.org/time-horizons/)

AGI를 논할 때도 같은 구분이 필요하다. 설계를 잘 제안한 사례는 설계 능력의 단서이고, 장시간 작업의 성공은 지속 수행 능력의 단서다. 서로 다른 분야와 낯선 조건에서 충분한 신뢰도로 반복되는지까지 봐야 더 넓은 결론에 다가갈 수 있다.

GPT‑6를 계기로 내가 주목하는 변화는 사람이 맡기는 판단의 범위다. 구현 방법을 일일이 정하던 작업에서 목표·제약·완료 기준을 제시하고 설계와 실행을 함께 맡기는 쪽으로 넓어질 수 있다. 기존 사용자에게는 그 가능성을 자신의 과제로 시험하고, 이를 막던 불필요한 절차를 고칠 기회다. AGI에 대한 기대도 그 과정에서 실제로 줄어든 개입과 반복해서 확인한 결과를 바탕으로 쌓는 편이 좋겠다.
